# S3 result: Binder over shared memory

**Status:** in progress, round 1 (Windows transport only; libbinder not yet on top).
**Code:** [`spikes/s3/`](../../../spikes/s3/) (standalone Cargo project, throwaway).

## Question

Does a shared-memory Binder reach a round trip under 20 µs on Windows, with
correct caller identity?

Round 1 answers the transport half: the shared memory layout, the wake
mechanism, the copy path, handle passing, death notification and caller
identity, measured between a broker and two client processes. libbinder on
top, and its tests, are round 2.

## Design built and measured

Three processes: a **broker** (stands in for sysd's Binder module), client
**A** (runs the benchmarks) and client **B** (serves transactions; optionally
started inside an AppContainer). One binary, `s3.exe`; the broker starts the
clients.

### Bootstrap and caller identity

1. The client opens a local-only, message-mode named pipe
   (`PIPE_REJECT_REMOTE_CLIENTS`, first instance flag against squatting,
   DACL: SYSTEM, the user, `ALL APPLICATION PACKAGES` read/write, low
   integrity label so AppContainer clients can write). The client opens it
   with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, so the broker can
   identify but not impersonate it.
2. The client sends a hello that includes a *claimed* pid. The broker ignores
   it (client B deliberately claims pid 4 to prove this).
3. The broker takes the pid from `GetNamedPipeClientProcessId`, the token of
   the writing thread from `ImpersonateNamedPipeClient` + `OpenThreadToken`
   (requires identification level, else rejected), and the process token
   from `OpenProcess` + `OpenProcessToken`. User SID and AppContainer SID of
   the two tokens must match, and the pid must equal the pid of the process
   the broker started. Otherwise the client is rejected.
4. The uid is derived from the AppContainer SID (spike rule; production uses
   the uid assigned at install).
5. The broker creates the channel section and events and `DuplicateHandle`s
   them into the client; handle values go back in the pipe reply. The client
   also receives a `SYNCHRONIZE` handle to the broker and exits if the broker
   dies (as apps die with system_server on Android).

In production sysd starts app processes itself, so it holds the process
handle from `CreateProcess` and can bind the channel to it without the pid
lookup; the pipe handshake is for processes it did not start (the manager).

### Channels

- **Per process, per thread role ("lane"):** one pagefile-backed section per
  client with two lanes (lane 0: the client's outgoing calls, lane 1:
  incoming transactions). Each lane has two single-producer/single-consumer
  byte rings (256 KiB each), client to broker and broker to client.
- **Message:** 64-byte header (kind, flags, length, code, peer, sender pid
  and uid stamped by the broker, transaction id, handle, two arguments) plus
  payload padded to 64 bytes. The consumer copies the header out and
  validates the length against the ring before use; a malformed record
  closes the ring.
- **Copies:** the sender writes the parcel into its ring (the copy a kernel
  driver does from user memory). Broker-local calls are read in place. For a
  call to another client the broker copies once, from the sender's ring slot
  straight into the receiver's ring slot, stamping identity and translating
  handles on the way. The receiver copies the payload out of shared memory
  before parsing (the sender could still be writing to it).
- **Relay:** the broker gives each forwarded transaction its own id and
  remembers (caller, lane, target, original id). A reply is accepted only
  from the client the transaction was sent to.
- **Direct pair channel (measured as an option):** the broker creates a
  section with two rings shared only by A and B and hands each end to its
  client, with the peer's identity attached by the broker. Data then moves
  without the broker; handles and binder objects could not, so this is only
  usable for plain-data traffic.

### Wake mechanism

Per ring: a `waiting` flag in shared memory and an auto-reset event.
Producer: publish the tail (SeqCst), and if `waiting` is set, clear it and
`SetEvent`. Consumer: spin for a budget, then set `waiting`, re-check the
tail, and only then `WaitForSingleObject`. A stale signal causes at most one
spurious wakeup. Spinning only happens while the ring is *hot* (a message in
the last 2 ms), so idle threads always sleep in the kernel and two threads
pinned to one CPU cannot starve each other for long.

Variants measured:

| Name | Behavior |
| --- | --- |
| `event` | no spinning; `SetEvent` then `WaitForSingleObject` |
| `event+SOAW` | no spinning; "wake the peer and sleep" in one `SignalObjectAndWait` call |
| `spin5us+event` | spin up to 5 µs per wait, then event |
| `spin50us+event` | spin up to 50 µs per wait, then event |
| `spin-while-hot` | spin while the ring is hot (2 ms after the last message), then event |
| `named pipe` | kernel IPC baseline: `TransactNamedPipe` on a message-mode pipe |

Primitives ruled out by a probe (`s3 probe`), confirmed on this machine:

| Primitive | Cross-process? | Probe result |
| --- | --- | --- |
| `WaitOnAddress` / `WakeByAddressAll` on a shared page | No | Waiter in the other process slept until its 1000 ms timeout |
| Keyed events (`NtWaitForKeyedEvent` / `NtReleaseKeyedEvent`, shared handle) | No | Release timed out (`0x102`), waiter timed out: keys only match within one process |
| `NtAlertThreadByThreadId` | No (documented in-process only by design) | not probed |
| ALPC | Yes | not measured: undocumented API; it is a kernel message copy like the named pipe baseline, so it cannot beat shared memory plus a direct wake |

## Results

### Machine and method

- Intel Core Ultra 7 258V (4 performance cores = logical CPUs 0-3, 4
  low-power efficiency cores = 4-7, no SMT), 32 GB, Lenovo laptop (83LC),
  Windows 11 Pro build 26300, **on battery, Balanced power plan**.
- **Not a quiet machine:** 30-50% total CPU from other workloads (other
  builds, Docker, browsers) during the runs. Tails (p99 and above) are
  dominated by this and must be re-measured on the reference PC.
- Rust 1.92.0, `x86_64-pc-windows-msvc`, release build.
- `s3 --iters 20000`: 20000 timed round trips after 2000 warm-up per row,
  three full runs; tables show the median over the runs (and the range of
  the p50s). Latency is `Instant` (QPC, 100 ns resolution) around one call.
- CPU per round trip: user + kernel time of all three processes from
  `GetProcessTimes`, divided by the calls. Its granularity is about
  0.7 µs per round trip here, so small values are approximate.
- Pinning plan (`pinned = yes`): caller A on CPU 1, broker threads serving A
  on CPU 2, broker threads serving B on CPU 3, B on CPU 0.
- Request sizes 100 B and 64 KiB; the reply is always 100 B.
- Paths: `A<->broker` (a call to a service in sysd, two wakes per round
  trip), `A->br->B` (app to app through the broker, four wakes),
  `A<->B direct` (pair channel, two wakes).

Pinning made almost everything worse on this machine: `SignalObjectAndWait`
went from 5.9 to 20.9 µs, spinning got unstable (one configuration hit a
steady ~550 µs in two of three runs), and 64 KiB copies took 15 µs instead
of 5.5 µs. A likely cause, not verified: when pinned, the woken thread must
run on one specific other core, which may be idle in a deep C-state or busy
with other load; unpinned, the scheduler can run it on the core that the
signaling thread is about to leave.

### Idle CPU

All three processes, 1 s without traffic, after each wake mode: **0.00%** in
every mode, including `spin-while-hot`, because no thread spins once its
ring has had no message for 2 ms.

### Oneway calls (100 B, pinned, 100000 calls then one synchronous call)

| wake | path | ns per call (3 runs) | CPU µs per call |
| --- | --- | --- | --- |
| event | A->broker | 341 / 290 / 427 | 0.3-0.6 |
| event | A->br->B | 642 / 846 / 564 | 1.3-1.9 |
| spin50us+event | A->broker | 189 / 314 / 210 | 0-0.6 |
| spin50us+event | A->br->B | 320 / 421 / 426 | 0.9 |

That is 1.2 to 5 million oneway calls per second; the sender only blocks
when the 256 KiB ring is full.

### Handle passing

- Functional: A writes into an anonymous pipe, passes the read handle in a
  transaction to B; the broker `DuplicateHandle`s it from A into B (also into
  the AppContainer B); B reads the exact text and sees A's pid as stamped by
  the broker. Verified in every run.
- No leak: B's handle count was identical after the first and the last of
  22000 passes (B closes each received handle).
- Cost (relayed call carrying one handle, 100 B, unpinned): p50 **4.1 µs**
  with `spin50us+event` (vs 1.0 µs without a handle, so about 3 µs for the
  duplicate into another process plus the close), 41.7 µs with `event`.

### Death notification

B links to A's death (on receiving A's pair offer, like `linkToDeath` on a
received binder). The broker waits on each client's process handle. From
A's last timestamp before `exit` to:

| run | broker sees the process handle signaled | B receives the death notice |
| --- | ---: | ---: |
| 1 | 4.42 ms | 4.48 ms |
| 2 | 7.52 ms | 7.75 ms |
| 3 | 4.53 ms | 4.60 ms |
| AppContainer B | 5.98 ms | 6.05 ms |

Almost all of it is process teardown before the handle is signaled; the
notice itself takes 60-230 µs to reach a sleeping B. Death notification is
asynchronous on Android too, so milliseconds are acceptable.

### Caller identity, including an AppContainer client

With `s3 --appcontainer`, client B runs in a fresh AppContainer profile
with no capabilities. The broker reported for B:

- claimed pid 4 (ignored); pipe client pid = the pid the broker started;
- impersonation level 1 (identification), as requested by the client's SQOS;
- the user SID, `AppContainer: true`, the AppContainer SID
  `S-1-15-2-1522723642-...`, integrity RID `0x1000` (low);
- process token and impersonation token agree.

A (not in a container) reported medium integrity (`0x2000`), no AppContainer
SID. Every relayed transaction carried the sender pid and uid stamped by the
broker. All transport features (relay, pair channel, handle passing into the
container, death notice) worked with B in the AppContainer; its latency rows
were in the same range as the plain runs (single run, so not compared
further).

### Cross-compilation and ARM64

- `x86_64-pc-windows-msvc`: builds, `cargo clippy -D warnings` clean.
- `x86_64-pc-windows-gnullvm`: Rust code compiles; linking failed with
  "linker `x86_64-w64-mingw32-clang` not found" because llvm-mingw was still
  being installed (`C:\tools\llvm-mingw.partial`). Retry once installed.
- ARM64: not measured; this machine is x64 only. The ring code uses only
  atomics with explicit orderings, so it is expected to be correct on ARM64,
  but its numbers must come from the ARM64 reference PC.

## What the numbers say

1. **The target is met for the common case.** An app calling a service in
   sysd (two wakes) takes **0.4 µs** p50 with bounded spinning and **5.9 µs**
   with no spinning at all (`SignalObjectAndWait`). App to app through the
   broker (four wakes) takes **1.0 µs** and **12.2 µs**. All are under 20 µs
   at p50 on a loaded laptop on battery.
2. **The kernel wake dominates.** A cross-process event wake costs about
   3 µs with `SignalObjectAndWait` and 6-9 µs with separate `SetEvent` and
   wait calls. Copying is cheap in comparison: one 64 KiB copy is about
   2.5 µs.
3. **Shared memory plus events beats kernel message IPC.** The named pipe
   baseline is 28 µs for 100 B, five times slower than shared memory with
   `SignalObjectAndWait`.
4. **Spin budgets must cover the whole reply time.** A 5 µs spin helps a
   direct call but hurts the relayed one (42 µs): the caller and the broker
   thread wait longer than 5 µs, give up, and pay for the kernel wake anyway.
   50 µs, or spinning while the ring is hot, covers it.
5. **Spinning has a cost under load.** Unbounded spinning while hot gave the
   best p50, but its p99.9 was poor on this busy machine (spinning threads
   take CPU from the threads they wait for), and it costs CPU per call:
   up to 60 µs per 64 KiB relayed round trip, with four threads spinning
   while one copies.
6. **Tails are a scheduler problem.** Every mode has p99.9 in the hundreds
   of µs or worse here. Whether this holds on a quiet reference PC on mains
   power is the main open measurement.
7. **The direct pair channel is not worth it.** It saves about 0.6 µs over
   the broker relay with spinning, and it cannot translate handles or binder
   objects or stamp identity per call.

## Recommendation

- **Transport:** keep this design: one section per process, per-thread lanes
  of SPSC rings, the broker copies once from sender's ring to receiver's
  ring, stamping identity and translating handles. No direct pair channels.
- **Wake:** shared-memory `waiting` flag plus an auto-reset event per ring;
  "send reply and wait for the next request" (and "send call and wait for the
  reply") as one `SignalObjectAndWait`; adaptive spinning before sleeping,
  bounded per wait (tens of µs, to be tuned) and only while the ring is hot,
  so idle cost stays zero.
- **Do not pin threads.** Leave placement to the scheduler; revisit ideal
  processor hints only with data from the reference PCs.
- **Rejected:** `WaitOnAddress` and keyed events (do not cross processes,
  verified), `NtAlertThreadByThreadId` (in-process), named pipes and ALPC for
  the data path (kernel copy, slower).
- **Identity:** sysd starts app processes itself and binds each channel to
  the process handle it got from `CreateProcess`; the pipe handshake with
  identification-level SQOS and token cross-checks is for processes it did
  not start (the manager). No ADR yet: this confirms the architecture in
  [03-components](../../spec/03-components.md#andruna-binder) rather than
  changing it. The wake choice becomes an ADR when round 2 confirms it.

## What remains (round 2 and later)

- libbinder unchanged on top: map `BINDER_WRITE_READ` and the other ioctls
  in `andruna-lx` onto these rings, then run libbinder's own tests that
  apply. Binder semantics not built here: thread pool (`BR_SPAWN_LOOPER`),
  nested and recursive transactions, reference counting, binder object
  translation, `BR_DEAD_REPLY` when the target dies mid-call (not
  implemented), oneway async buffer limits, transaction size limits.
- Broker threading: the spike uses one broker thread per lane, which does
  not scale. Choose a pool design (for example a thread per client process
  plus overflow), and measure with many clients.
- Measurements on the quiet x64 reference PC on mains power, and on the
  ARM64 reference PC; tune the spin budget; measure power impact of spinning
  on battery.
- Security hardening: per-package SIDs in the pipe DACL instead of
  `ALL APPLICATION PACKAGES`; restrict passable handle types (files, pipes,
  sockets, sections, sync objects) by querying the object type before
  duplicating; fuzz the ring parser; a malicious producer can only corrupt
  its own rings, which the consumer validates.
- Build with `x86_64-pc-windows-gnullvm` and `aarch64-pc-windows-gnullvm`
  once llvm-mingw is installed.

## Reproduce

```
cd spikes/s3
cargo build --release
target\release\s3.exe --iters 20000            # plain clients
target\release\s3.exe --appcontainer --iters 20000   # B in an AppContainer
target\release\s3.exe probe                    # cross-process wake probes
```

`--appcontainer` grants `ALL APPLICATION PACKAGES` read and execute on the
build output directory (so the container can load the binary) and deletes
the AppContainer profile at the end.
