## 1. Fault delivery (VEH to Linux signal handler)

Implemented in [`signals.rs`](../../../spikes/s1/src/signals.rs): a Vectored
Exception Handler (first in the chain) maps

| Windows exception | Linux signal |
| --- | --- |
| `STATUS_ACCESS_VIOLATION`, `STATUS_GUARD_PAGE_VIOLATION`, `STATUS_STACK_OVERFLOW` | `SIGSEGV` (`SEGV_MAPERR` / `SEGV_ACCERR` from `VirtualQuery`) |
| `STATUS_IN_PAGE_ERROR` | `SIGBUS` (`BUS_ADRERR`) |
| `STATUS_ILLEGAL_INSTRUCTION`, `STATUS_PRIVILEGED_INSTRUCTION` | `SIGILL` (`ILL_ILLOPC`) |
| `STATUS_INTEGER_DIVIDE_BY_ZERO`, `STATUS_INTEGER_OVERFLOW` | `SIGFPE` (`FPE_INTDIV`, `FPE_INTOVF`) |

It builds a bionic `siginfo_t` and `ucontext_t` (x86_64: general registers,
`CSGSFS`, `ERR`/`TRAPNO`/`CR2`, FXSAVE image; arm64: `x0-x30`, `sp`, `pc`,
`pstate`, `fault_address`, `fpsimd_context` and `esr_context` records), calls
the `SA_SIGINFO` handler (on the `sigaltstack` stack when `SA_ONSTACK` is
set), writes the possibly modified context back and resumes, as
`rt_sigreturn` does. An unclaimed signal goes back to `SIG_DFL` and the
re-executed fault reaches Windows' default handling, as libsigchain does.

Layouts are checked at compile time against bionic's headers (bionic main,
read on 2026-11-26) for **both** architectures on every build
([`linux_abi.rs`](../../../spikes/s1/src/linux_abi.rs)). Note: bionic's x86_64
`ucontext_t` is 816 bytes (no padding after the 8-byte `uc_sigmask`, unlike
the 936-byte glibc layout); arm64 is 4560 bytes with `uc_mcontext` at 176.

| Result | Value |
| --- | --- |
| Implicit null check (load from `null + 8` in JIT-buffer code; handler pushes `pc + 3` and redirects to an NPE stub, as ART's x86_64 handler does; stub records the pushed address and continues in the method's catch block) | correct |
| `ud2` -> `SIGILL`, `div` by zero -> `SIGFPE`, handler skips the instruction | correct |
| Load without fault (baseline) | 1.2 ns |
| **Fault round trip, full path** (VEH + ucontext conversion + handler + write-back) | **1.25-1.35 µs** (one run under heavy load: 2.96 µs) |
| Same, handler on the alternate stack | 1.29-1.32 µs |
| Windows exception dispatch alone (VEH redirects without conversion) | 1.16-1.20 µs |
| Faulting-thread stack used by kernel exception frame + ntdll dispatcher before the VEH frame | 2.6-2.7 KiB |

So the conversion and handler cost about 0.1 µs; the rest is the kernel
and ntdll dispatch, which we cannot reduce. An implicit null check that
actually fires costs about 1.3 µs; ART only takes that cost when a null is
dereferenced (exception path), so it is acceptable.

### Stack overflow

**ART-style implicit check** (`test [rsp - 8 KiB], eax` in every frame of
the generated code, a 16 KiB `PAGE_NOACCESS` protected region near the stack
bottom, handler redirects to a stub that restores the entry frame's SP):
caught 3 of 3 at depth 7850-7859 frames on a 1 MiB thread; faulting SP was
8.0 KiB above the protected region, of which the dispatcher used 2.7 KiB.
It also works with the handler on the faulting stack (tested in a child
process), but ARM64's 4.5 KiB ucontext would not leave margin, so **the
alternate stack should always be used**.

The alternate stack is entered by a small assembly routine that switches SP
and temporarily sets the TEB's `StackBase`/`StackLimit` to the alternate
stack, so exception dispatch and unwinding on it pass the dispatcher's
stack-bounds checks (it has SEH unwind info with a frame pointer, so
unwinding through it back to the faulting stack works).

**Finding: the probe needs a committed stack.** ART probes 8 KiB below SP.
On a Windows stack that grows through a one-page guard page, the probe jumps
over the guard page into reserved, uncommitted memory and faults as a plain
access violation; ART's stack would never grow. Java threads therefore need
their whole stack committed (lx's `pthread_create` passes the stack size as
the commit size; the main thread must not run managed code, or its stack
must be committed). This costs commit charge, not physical memory, for
untouched pages. Committing a page also stops Windows from moving its guard
page over our protected region.

**Windows' own overflow** (guard page, `SetThreadStackGuarantee(32 KiB)`,
recursion without probes): 3 of 3 raised `STATUS_STACK_OVERFLOW`, delivered
as `SIGSEGV`, redirected to the stub, at depth 419-420 frames of a 256 KiB
reserved stack. After each overflow the spike re-arms the guard pages by
hand (what the CRT's `_resetstkoflw` does) before the next round; behavior
without re-arming was not tested. This path is the fallback for native
code, not for ART.

## 2. Thread suspension

Implemented in [`suspend.rs`](../../../spikes/s1/src/suspend.rs). Four
mechanisms on N worker threads running a tight loop:

- **StopOnly**: `SuspendThread` + `GetThreadContext` (stop and read the
  context; no code runs on the target).
- **Inject** (signal-style): suspend, `GetThreadContext`, set RIP to a
  trampoline and RSP below the 128-byte red zone, `SetThreadContext`,
  resume. The trampoline captures the **live** registers with
  `RtlCaptureContext` (only RIP, RSP and RCX are repaired from saved
  values), runs the checkpoint, and resumes with `RtlRestoreContext`.
- **Flag**: cooperative poll of a flag per loop iteration (ART's explicit
  suspend check, used on x86_64).
- **Page**: cooperative load from a page that the requester protects to
  force a fault; the SIGSEGV handler runs the checkpoint (the global form of
  ART's implicit suspend check, which ART uses on arm64 with a per-thread
  trigger pointer).

Suspended threads block on `WaitOnAddress` (as lx's futex will).

Overhead on the running thread (one thread pinned to one CPU, million loop
iterations per second, median of 5): no check 464 / flag poll 463 / page
load 471 (second run: 930 / 952 / 956). The difference is within noise: a
load and a predictable branch per iteration are hidden by the out-of-order
core in this loop. ART's real cost is measured when ART runs.

Latency until all N threads have stopped:

| Mechanism | N=1 median (p99) | N=4 median | N=8 median | N=32 median |
| --- | --- | --- | --- | --- |
| StopOnly | 6-30 µs (27-119) | 0.15-0.17 ms | 0.08-6.1 ms | 2.5-23 ms |
| Inject | 28-70 µs (152-6146) | 0.8-2.1 ms | 7.0-9.1 ms | 34-150 ms |
| Flag | **0.1-0.2 µs** (0.3) | 1.2-3.2 ms | 4.0-4.7 ms | 19-20 ms |
| Page | 4.2 µs (14-2401) | 1.3-2.8 ms | 4.2-4.7 ms | 16-27 ms |

Ranges are over two full runs (three for StopOnly). The p99 column shows
how much a single descheduled thread costs on this machine.

At N=1 the cost of the mechanism itself shows: cooperative polling is about
100 times faster than anything that goes through the kernel, and the
protected page (one `VirtualProtect` plus one fault) costs about the same as
a single `SuspendThread` + `GetThreadContext`. At N >= 4 on this loaded
laptop all four are limited by how soon each thread gets a CPU again; for
injection and StopOnly, `GetThreadContext` on another thread has to wait for
that thread to be scheduled, so they are the slowest under load. These rows
need the reference PC.

### Hazards (measured)

- **Thread blocked in a system call.** A thread waiting in
  `WaitForSingleObject` was suspended; its captured RIP was just after a
  `syscall` instruction with RAX = 0x4 (the system call number). After
  injection, the checkpoint did **not** run while the thread was blocked; it
  ran only after the event was signaled, and the wait still returned
  `WAIT_OBJECT_0` because the trampoline captured the live RAX (the kernel's
  return value) instead of restoring the RAX read at suspension. Injection
  therefore cannot interrupt a blocking call (unlike a Linux signal, which
  makes it return `EINTR`), and an injector that restores the suspended
  register set would corrupt system call results.
- **Heap lock.** A thread allocating 64 KiB blocks in a loop was suspended
  500 times; in **402 of 500** (80%) it held the process heap lock, so any
  allocation by another thread (or by code injected into it) would block
  until it resumes. The same applies to the loader lock and any lock in
  Windows or the CRT. Code that runs while another thread is suspended at an
  arbitrary instruction, or code injected into it, must be async-signal-safe
  in the Linux sense: no heap, no loader, no locks shared with arbitrary code.
- **Vector state.** `RtlCaptureContext`/`RtlRestoreContext` save XMM but not
  the upper halves of YMM (AVX). ART's x86_64 compiler can emit AVX2. A
  production injector would need `RtlCaptureContext2` with `CONTEXT_XSTATE`.

### How ART's own design interacts

ART does not use signals to suspend threads. Suspension and checkpoints are
cooperative: a request sets flags in each thread's state word; runnable
threads see it at suspend checks (explicit flag tests on x86_64, a load
through a per-thread trigger pointer that faults on arm64); threads in
native code or blocked are already "suspended" in ART's sense, and the
requester runs checkpoints on their behalf. Checkpoints must run at a safe
point (consistent stack, mutator lock state), so running them from an
injected interrupt would be wrong even if it were fast. The uses of signals
around ART are elsewhere: `SIGQUIT` handled by the signal-catcher thread
with `sigwait` (a process-directed signal, not suspension), and native stack
dumps of other threads, which on Linux interrupt the thread only to read its
registers; on Windows `SuspendThread` + `GetThreadContext` gives the same
without running code on the target.

### Recommendation

**Cooperative suspension only for ART** (no change to ART): explicit checks
on x64, implicit suspend-trigger faults through the VEH on ARM64 (about
1.3 µs per triggered check, paid only when a suspension is requested).
lx implements `sigwait`/`sigtimedwait` and process-directed signals for the
signal catcher, and offers "stop thread and read registers" with
`SuspendThread` + `GetThreadContext` for stack dumps. Signal-style injection
is **not** needed for ART; keep the prototype for guest native code that
sends real asynchronous signals between its own threads (for example game
engines whose garbage collectors stop threads with `pthread_kill`), to be
decided in phase 5 with the live-register and XSTATE rules above.

## 3. Calling convention on x64

Implemented in [`abi.rs`](../../../spikes/s1/src/abi.rs) and
[`arch_x64.rs`](../../../spikes/s1/src/arch_x64.rs).

| Test | Result |
| --- | --- |
| Hand-written System V function calling Windows-ABI code (`cb(2a, 3b) + 1`) | correct |
| `s1_sysv_to_win64` trampoline, 6 integer args (4 to `rcx, rdx, r8, r9`, 2 on the stack above the 32-byte shadow space) | correct |
| `s1_win64_to_sysv` trampoline, 4 args, saves `rsi`, `rdi`, `xmm6-xmm15` | correct |
| Register harness: a System V function that clobbers what System V allows, called directly as if it were Windows code | `rsi`, `rdi`, `xmm6-xmm15` clobbered (mask `0x3ff0c`) |
| Same through the trampoline / through a rustc `extern "sysv64"` call from Windows-ABI code | nothing clobbered |

| Call (ns per call, quiet run / loaded run) | ns |
| --- | --- |
| Windows -> Windows | 0.7-0.9 / 1.5 |
| Windows -> System V, compiler-generated saves | 2.5-2.8 / 4.3 |
| Windows -> System V, hand trampoline | 2.5-2.7 / 4.5 |
| System V -> Windows, hand trampoline | 1.2 / 5.0 |

Rules confirmed:

- **System V -> Windows is cheap.** Windows' volatile set is a subset of
  System V's, so the caller only remaps arguments (args 5+ go on the stack),
  reserves 32 bytes of shadow space and keeps RSP 16-byte aligned at the
  call. Nothing needs saving.
- **Windows -> System V is the expensive direction** (about +1.8 ns): System
  V code may clobber `rsi`, `rdi` and `xmm6-xmm15`, which Windows callers
  expect preserved, so the boundary saves 12 registers (176 bytes).
- clang and rustc generate both transitions for functions declared with the
  other convention (`__attribute__((sysv_abi))`, `extern "sysv64"`).

**How JNI natives built as Windows code are entered.** ART's JNI stubs
(compiled per method, or the generic JNI trampoline) call the native with
System V on x86_64, and `JNIEnv` functions are called by natives with the
`JNICALL` convention. Recommendation: in our build, `JNICALL` (and
`JNIEXPORT` functions) are `__attribute__((sysv_abi))` on x64, as the
architecture spec already states. Then the native's own C/C++ is ordinary
Windows code and clang inserts the save of `rsi`, `rdi`, `xmm6-15` in the
native's prologue; ART's stub needs no change. The other boundary is where
Windows-ABI C++ enters managed code and runtime stubs:
`art_quick_invoke_stub` and friends (called from C++), and the `artXxx`
runtime entrypoints (called from the hand-written x86_64 assembly
stubs). Each needs its C++ declaration marked `sysv_abi` under `ANDRUNA`
(one macro on the declarations; clang then generates the transitions). The
assembly stubs themselves stay System V. Guest ELF code (System V) entering
our Windows-ABI libraries goes through generated thunks (phase 5), which are
the `s1_win64_to_sysv` pattern in reverse.

### Unwind info for generated code

| Registration of the JIT buffer's unwind data | Fault inside JIT code, `RtlVirtualUnwind` from the fault context | Manual walk (`RtlLookupFunctionEntry` + `RtlVirtualUnwind`) from a callback called by JIT code | `RtlCaptureStackBackTrace` from that callback | Rust panic unwinding through the JIT frame (child process) |
| --- | --- | --- | --- | --- |
| none | wrong (treated as leaf) | wrong | stops at the JIT frame | **process terminated** (`0xE06D7363` unhandled) |
| `RtlAddFunctionTable` | correct | correct | stops at the JIT frame | caught |
| `RtlInstallFunctionTableCallback` | correct | correct | stops at the JIT frame | caught |
| `RtlAddGrowableFunctionTable` | correct | correct | stops at the JIT frame | caught |

The unwind data was hand-made (x64 `UNWIND_INFO` with push/alloc codes; for
ARM64, packed unwind data, written but not run). Findings:

- Without unwind data, any exception that has to be dispatched through a
  managed frame (an SEH exception, a C++ exception or panic, an unwinding
  `longjmp` in mingw/UCRT) terminates the process. ART itself unwinds
  managed frames with its own stack walker and never needs this, but native
  code called from managed code does.
- `RtlCaptureStackBackTrace` never walks past a frame outside a loaded
  image, whatever the registration; tools that use it (and possibly crash
  reporting and ETW stack sampling, not tested) will show truncated stacks
  in managed code.
- Recommendation for ART: the JIT code cache uses one
  `RtlAddGrowableFunctionTable` (extended with `RtlGrowFunctionTable` as
  methods are committed) or one callback over the whole cache that builds
  the entry from the method header (frame size and spill masks are there).
  AOT code in ELF oat files is loaded by ART's own loader, not as a PE
  image, so it needs the same registration per oat file. ART's x86_64 frames
  save floating-point callee-saves with 8-byte stores, which Windows unwind
  codes cannot describe exactly (`UWOP_SAVE_XMM128` is 16 bytes); that only
  matters for code resumed after an unwind, so a frame description without
  them is acceptable.

### How the code is compiled

AOSP code is compiled as Android code for a Windows target: clang
`--target=<arch>-w64-windows-gnu` (COFF, Windows calling convention, the

### Data model

This is the main finding of the round. Windows targets are **LLP64**
(`long` is 32 bits); Android's 64-bit ABI and andruna-lx's exports are
**LP64**. clang offers no option to change `long` on a Windows target.
The build defines `__LP64__` (so bionic and ART select their 64-bit
layouts), widens the kernel's `__kernel_long_t` to `long long` in a forced
header (so `size_t`, `ssize_t`, `off_t`, `time_t`, `clock_t` are 64 bits),
and patches `stdint.h`/`inttypes.h`. What remains different was measured
by compiling the same bionic headers both ways
(`aosp/tools/data_model/compare.py`; Android column: clang
`--target=<arch>-linux-android35`, same headers, no ANDRUNA):

| Type or field (bytes) | x64 Andruna | x86_64 Android | arm64 Andruna | arm64 Android |
| --- | ---: | ---: | ---: | ---: |
| `long` | 4 | 8 | 4 | 8 |
| `size_t`, `ssize_t`, `off_t`, `time_t`, `int64_t`, `intptr_t` | 8 | 8 | 8 | 8 |
| `struct timespec` / `tv_nsec` | 16 / 4 | 16 / 8 | 16 / 4 | 16 / 8 |
| `struct stat` | **128** | 144 | 128 | 128 |
| `offsetof(stat, st_blocks)` / `st_atim` / `st_mtim` | **60 / 64 / 80** | 64 / 72 / 88 | 64 / 72 / 88 | 64 / 72 / 88 |
| `struct statvfs` / `f_blocks` offset | **68 / 8** | 112 / 16 | **68 / 8** | 112 / 16 |
| `sigset_t` | **4** | 8 | **4** | 8 |
| `ucontext_t` / `uc_sigmask` offset | **696 / 176** | 816 / 296 | 4560 / 40 | 4560 / 40 |
| `greg_t` (x86_64 `uc_mcontext.gregs[]`) | **4** | 8 | | |
| `jmp_buf` | **44** | 88 | **128** | 256 |
| `pthread_t` | **4** | 8 | **4** | 8 |
| `rlim_t`, `fd_mask`, `blkcnt_t` | **4** | 8 | **4** | 8 |
| `long double` | 16 | 16 | **8** | 16 |
| `struct sigaction` (size; its `sa_mask` is the 4-byte `sigset_t`), `siginfo_t`, `stack_t`, `pthread_mutex_t`, `pthread_cond_t`, `pthread_attr_t`, `dirent`, `msghdr`, `iovec`, `epoll_event`, `pollfd`, `fd_set`, `wchar_t` | same | | same | |

Consequences, with the evidence:

- **Buffer overruns against lx as merged.** andruna-lx's `StatX86_64` is
  144 bytes (`crates/andruna-lx/src/linux/stat.rs`, asserted). An x64 AOSP
  caller allocates 128 bytes for `struct stat`, so `fstat` from lx writes
  16 bytes past the caller's buffer, and the caller reads `st_atim` and
  later fields at the wrong offsets. `statvfs` (68 vs 112) and `jmp_buf`
  (44 vs 88 on x64, 128 vs 256 on arm64) are the same kind.
- **Silent truncation of values.** `pthread_t` is a pointer in bionic: a
  64-bit value returned by lx is cut to 32 bits. `sigset_t` holds 32
  signals instead of 64, so masks for real-time signals are lost.
  `long`-returning functions (`syscall`, `sysconf`, `strtol`, `ftell`,
  `lseek` through `long` variables) return 32 bits to AOSP code; lx's
  `syscall` returns `i64` and AOSP code keeps the low half.
- **Undefined upper halves.** When AOSP code passes a `long` argument, or
  writes a `long` field (`timespec::tv_nsec`), only 32 bits are defined.
  Example from the build (`ANDRUNA_AOSP_WARNINGS=ON`,
  `-Wshorten-64-to-32`): `art/libartbase/base/time_utils.cc:225` and
  `system/libbase/properties.cpp:229` store a 64-bit value into
  `tv_nsec`. lx reads `tv_nsec` as `i64` and rejects values outside
  `[0, 1e9)`, so a timed wait from ART can fail with `EINVAL` depending on
  stack garbage. lx's `syscall` reads every argument as `i64`; an `int` or
  `long` argument from AOSP code has undefined upper bits under the
  Windows ABI.
- **ART's fault handler on x64.** `greg_t` is `long`, so
  `uc_mcontext.gregs[REG_RIP]` in `runtime/arch/x86/fault_handler_x86.cc`
  indexes 4-byte slots: the handler reads and writes the wrong registers
  of the 816-byte context that lx builds. arm64 is not affected (its
  `mcontext_t` uses `unsigned long long` and fixed-size fields).
- **`long double` on arm64** is 64-bit on Windows and 128-bit on Android:
  `strtold`, `printf("%Lf")` and any `long double` in a struct differ.
- **Variadic calls on arm64.** Windows ARM64 passes floating-point
  variadic arguments in integer registers; AAPCS64 passes them in vector
  registers. A `printf` that AOSP code calls must be compiled with the
  Windows convention (an lx or bionic build for the Windows target), not
  bionic's Android build.
- **Inside AOSP code, `long` is mostly absent.** ART itself almost never
  uses `long` (`grep` finds no `sizeof(long)` assumption in libartbase,
  libdexfile or the runtime). In layers 1 and 2, `-Wshorten-64-to-32`
  reports 298 narrowing conversions, of which only **3** narrow to
  `long` (the two `tv_nsec` stores above and `liblog/logd_reader.cpp:190`).
  In the libart sources that compile on x64, 644 distinct narrowing sites,
  of which **1** narrows to `long`: `art/runtime/base/mutex.cc:497`, again
  a `tv_nsec` store, for the timeout of ART's own `futex` wait. No `-Wformat` warning in either (the `PRI*` patch
  keeps the format macros consistent).

Options:

1. **Stay LLP64, widen the ABI types in the headers.** Extend the bionic
   patch so that every ABI `long` in bionic's public and UAPI headers
   becomes a 64-bit type under `ANDRUNA` (struct fields, typedefs such as
   `greg_t`, `rlim_t`, `pthread_t`, `sigset_t`, `jmp_buf`, and the
   `long`-typed parameters and returns of functions such as `syscall`,
   `sysconf`, `strtol`, `ftell`). About 190 lines in `libc/include`, plus
   the UAPI structures that AOSP code passes to lx (`struct stat` comes
   from bionic, but `sigaction`, `rlimit`, `timespec` from UAPI also use
   `long`). Use `ANDRUNA_AOSP_WARNINGS` (`-Wshorten-64-to-32`) to find
   the AOSP code that still stores 64-bit values in `long`, and fix those
   with small patches. `compare.py` becomes a CI check that every probed
   layout matches Android. Cost: a large, mechanical bionic patch carried
   for every tag, an audit that grows with each AOSP project built
   (framework natives, HWUI, Skia), and `long double` on arm64 stays
   different.
2. **LP64 with the Windows calling convention.** clang's
   `x86_64-pc-cygwin` target is exactly that for x64 (checked: LP64,
   COFF, arguments in `rcx`; it uses emulated TLS by default). There is no
   ARM64 equivalent in clang, so arm64 would need an LLVM change (a new
   environment for `aarch64-windows` with 64-bit `long` and 128-bit
   `long double`), carried by us. Not tried further.
3. **Build AOSP as Android ELF code.** Compile AOSP with
   `--target=<arch>-linux-android` (true LP64, System V on x64, AAPCS64 on
   arm64, bionic exactly as on Android) and load it with andruna-linker,
   the same path as app native code. Every call into lx then crosses a
   System V or AAPCS64 to Windows boundary (cheap in this direction,
   round 1 section 3), and lx's guest-facing exports already have the
   right layouts. Costs: andruna-linker is needed in phase 0 instead of
   phase 5, debugging uses DWARF instead of PDB, and it changes the
   calling-convention table in 02-architecture and ADR 0008.

Recommendation: decide this in an ADR before andruna-lx's export ABI
grows. Option 1 keeps the current architecture and is measurable now
(compare.py and the warning build show every remaining difference), so it
is the default to continue with; option 3 is the cleaner ABI and should be
costed in round 3 (how much of andruna-linker phase 0 needs) before option
1's header patch is written.

### The x64 thread register (round 2, risk 1)

ART on x86_64 keeps the current `Thread*` in the GS base
(`arch_prctl(ARCH_SET_GS)`) and reads Thread fields as `%gs:offset` from
the assembly entry points, nterp and compiled code. On Windows x64 GS is
the TEB and cannot be repointed: user-mode `WRGSBASE` works on this CPU
(S4), but Windows code on the same thread needs GS = TEB, and a context
switch would silently restore it (no fault, unlike FS, so no lazy
restore is possible).

Decision for the spike: **the Thread\* is read through bionic's TLS slot
`TLS_SLOT_ART_THREAD_SELF`**, which ART already fills on Android for
`Thread::Current()` and which sits at `%fs:0x38` on x86_64. FS is the
guest thread pointer already (S4, S8: FS base with lazy restore), so no
new mechanism is needed. Three ART patches, all gated on `ANDRUNA`:

| Patch | Lines | What |
| --- | ---: | --- |
| `0001-x86_64-thread-self-through-fs-tls-slot` | +142 / -73 | Assembly entry points: `Thread::Current()` loads (43 sites) become one `movq %fs:0x38, %reg` (`GS_SELF`); the 18 other field accesses load the Thread\* into a register that is dead there (`LOAD_THREAD_FIELD_BASE r10` + `THREAD_FIELD(offset, r10)`, chosen per site; the lock fast paths reorder to use RAX). `Thread::InitCpu` stores the slot instead of `arch_prctl` and checks it. Without `ANDRUNA` the macros expand to the original `%gs:` forms. |
| `0002-x86_64-compiled-code-thread-through-fs-tls-slot` | +90 / -8 | Optimizing and JNI compilers: under `ANDRUNA`, `X86_64Assembler::gs()` emits `mov r11, fs:[0x38]` (R11 is the code generators' reserved TMP) and re-encodes the next instruction's absolute `[disp32]` operand as `[r11 + disp32]`; no call site changes except two JNI sites where R11 is an input (they pass RAX or a callee-save scratch register). |
| `0003-x86_64-no-nterp` | +7 / -1 | `IsNterpSupported()` is false on x86_64 under `ANDRUNA`: nterp's `rSELF:offset` accesses (about 25) are not ported yet, so the switch interpreter is used (with and without JIT). |

Cost, measured with `andruna-spike-s1-art tlscost` (a guest thread, 200 M
iterations, best of 5, three runs):

| Access | ns per access |
| --- | ---: |
| One segment-relative load (`fs:[off]`, the form of Android's `gs:[off]`) | 0.235 to 0.237 |
| `mov r11, fs:[0x38]` then load `[r11 + off]` (ANDRUNA) | 0.397 to 0.418 |
| `mov r11, fs:[0x38]` then store `[r11 + off]` | 0.235 to 0.240 |

A dependent load pays one extra L1 hit (about 0.17 ns, the latency of the
slot load); a store pays nothing measurable. `Thread::Current()` in the
stubs costs the same as on Android (one load). The FS base was reset and
lazily restored 300 to 457 times during each 3-run measurement (about one
per context switch), as S4 measured. Alternatives considered: a dedicated
register in ART's x86_64 back end (the ARM64 model, a large register
allocator change) and keeping `%gs:` with a swapped GS base (not safe: a
context switch would restore the TEB without a fault).

### The runner

`andruna-spike-s1-art run dalvikvm <options>` maps dalvikvm, then the
objects ART opens at start-up (`S1_PRELOAD`, default libart, libopenjdkjvm,
libicu_jni, libjavacore, libopenjdk) and their dependencies in one load,

- `dl.rs`: `dlopen` (returns the preloaded object; loads late objects
  without TLS), `dlsym` (per object, `RTLD_DEFAULT`, `RTLD_NEXT` = the
  host's function, which is how libsigchain finds the real `sigaction`),
  `dladdr`, `dl_iterate_phdr`, `android_dlopen_ext`; no namespaces.
- `signal.rs`: `sigaction`/`sigaction64` record guest handlers; the
  loader's first vectored exception handler, after the FS-base lazy

  bionic's x86_64 `siginfo_t`/`ucontext_t` (816 bytes, asserted), calls the
  handler on the faulting stack and resumes the context it leaves (round 1
  design, without the alternate stack). `pthread_kill` of a signal queues
  it for `sigwait*` (ART's signal catcher; the runtime's shutdown needs
  it). Masks are accepted and ignored.
- `lx.rs`: file-backed `mmap` as an anonymous private copy (lx has no

- `extra.rs`: `uname` (Linux 6.6), `pthread_getattr_np` (the TEB stack

### What does not work yet

1. **The JIT with `-Xjitthreshold:0` deadlocks** under allocation and
   compilation load: the main thread waits in `FullSuspendCheck` (a
   suspend request is pending), one JIT worker waits for a mutex inside
   the compiler, another in `JitCompiler::CompileMethod`; at shutdown a
   JIT pool worker loops in `ThreadList::Unregister` while the main thread
   joins it. Not diagnosed. Candidates: the `FUTEX_CMP_REQUEUE` emulation,
   lx futex wake-ups under contention, or a suspend request the runner
   never lets complete. The default thresholds, which compile far fewer
   methods, did not hit it in seven runs.
2. **AOT is not done**: dex2oat (compiler driver, linker, image writer) is
   not built, so there is neither a boot image nor AOT code. The JIT runs
   the same x86_64 back end under the FS slot that dex2oat would use.
3. **nterp is off** on x86_64 (patch 0003). Porting its ~25 `rSELF:`
   accesses with the macros of patch 0001 is the next ART patch.
4. **ARM64 was not built in this round.** The three patches are x64-only
   (ARM64 keeps the Thread in x19); the arm64 build, its nterp and the
   runner for `aarch64-pc-windows-gnullvm` are untried.
5. **Implicit stack-overflow checks are not verified**: StackOverflowError
   was thrown in both modes, but no stack fault reached the signal path,
   so the JIT code's stack probe and ART's protected region (which ART
   `mprotect`s through lx on a Windows thread stack lx does not own) are
   untested.
6. The libcore natives and ICU in these runs were linked before
   `-ftrivial-auto-var-init=zero` was added; ART was rebuilt with it. A
   rebuild of ICU and libcore with the flag is pending.
7. Runner shortcuts the product must replace: file `mmap` by copy (no
   sharing, no write-back), requeue as wake-up, signals only on the
   faulting stack, no masks, no asynchronous delivery to running threads,
   preloading instead of `dlopen` with dynamic TLS, unwinding of guest code
   for ART's native stack dumps (libunwindstack).

## Risks found

1. **Thread register on x64 (new, blocking).** ART on x86_64 sets the GS
   base to its `Thread*` with `arch_prctl(ARCH_SET_GS)` and its generated
   code and assembly stubs read thread fields with `%gs:` addressing. On
   Windows x64, GS is the TEB and user mode cannot change it (no
   `arch_prctl`, `wrgsbase` disabled). Options: (a) a dedicated thread
   register in ART's x86_64 back end and stubs (as ARM64 does with x19), a
   large patch; (b) keep `%gs:` but read `Thread*` from a fixed TEB slot
   first (two instructions and a scratch register per access); (c) map the
   needed `Thread` fields at a fixed offset from the TEB (not feasible). This
   needs an ADR before x64 ART can run; ARM64 is not affected (x19 is the
   thread register; x18/TEB is untouched by ART). Related to S4 (TLS).
   **Round 3:** a variant of (b) through FS instead of a TEB slot works:
   the Thread\* is read from bionic's `TLS_SLOT_ART_THREAD_SELF` at
   `%fs:0x38`; patches 0001 to 0003 in `patches/art/`, cost +0.17 ns per
   dependent field load ([Round 3](#the-x64-thread-register-round-2-risk-1)).
   Proposed as ADR 0015.
2. **Stacks must be fully committed** for ART threads (see section 1).
3. **CET shadow stacks.** Redirecting RIP from a VEH, `SetThreadContext`
   and `RtlRestoreContext` to arbitrary addresses conflicts with
   hardware-enforced stack protection if a binary opts in (`/CETCOMPAT`) in
   strict mode; it would need registered EH continuation targets
   (`SetProcessDynamicEHContinuationTargets`) for every stub ART redirects
   to. Not tested; our binaries are not CET-compatible today.
4. **Exception dispatch stack use** was 2.7 KiB here; on CPUs with AVX-512
   the XSAVE area in the context record is larger. ART's 8 KiB reserve still
   fits but must be re-measured on such a CPU and on ARM64.
5. **Other vectored handlers** added later with `first = 1` run before ours
   (injected DLLs, diagnostics tools). They normally return
   `EXCEPTION_CONTINUE_SEARCH`, but a misbehaving one could swallow ART's
   faults.
6. **errno and libc surface.** ART and libcore check `errno` after many libc
   calls. If any of those functions come from the UCRT, they set the UCRT's
   errno with different numbering (for example `ETIMEDOUT` is 138 in the
   UCRT and 110 on Linux). The whole errno-setting libc surface must come
   from one Linux-numbered implementation (lx, or bionic per S4).
7. **Debuggers.** Every implicit null check that fires is a first-chance
   exception; under a debugger this is slow and noisy. Debugging setups
   should ignore first-chance access violations in managed code.

### Stack overflow: ART's 8 KiB gap is not enough on Windows ARM64

ART's arm64 implicit check probes 8 KiB below SP. With that gap the spike's
ART-style overflow test **kills the process** (0xC0000005, three runs):
Windows' exception dispatch uses 7.1 KiB of the faulting stack before the
VEH can switch to the alternate stack, so the VEH's own frame runs into the
protected region and the nested fault is fatal. The spike now takes the gap
as a parameter (`S1_SO_GAP`):

| Gap below SP | Result (3 overflows each) | Faulting SP above the protected region |
| --- | --- | --- |
| 8 KiB (ART arm64 default) | process killed | |
| 12 KiB | caught 3 of 3, alt stack and on the faulting stack | 12.2 KiB |
| 16 KiB | caught 3 of 3, alt stack and on the faulting stack | 16.3 KiB |

**Consequence:** ART's arm64 stack-overflow reserved size
(`GetStackOverflowReservedBytes(kArm64)`, 8 KiB) must grow to at least
12 KiB, better 16 KiB, under `ANDRUNA` on Windows ARM64. That is one small
ART patch; it costs 8 KiB of usable stack per Java thread. (x64 VM: 4.5 KiB
of the 8 KiB gap used, so x64 works with ART's default but with less margin
than measured on the laptop, 2.7 KiB; 16 KiB is advisable there too.)
Windows' own guard-page overflow (`SetThreadStackGuarantee(32 KiB)`) was
delivered as `SIGSEGV` and redirected 3 of 3 at depth 428-429.
