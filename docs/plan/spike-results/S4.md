# S4 results: bionic and thread-local storage

**Status.** Round 1 (2026-11-26). The x64 thread-pointer question is answered
on one machine. The ARM64 tests ran on a GitHub-hosted Windows 11 ARM64
virtual machine (section 2): `TPIDR_EL0` is writable from user mode and
preserved per thread. Loading an NDK library with real bionic (stdio,
locale, malloc, pthread, C++ exceptions) is not started and is the next
round.

Code: [`spikes/s4/`](../../../spikes/s4/) (standalone Cargo project, not in
the workspace). `andruna-spike-s4 probe | bench | all` runs everything below;
`tools/scan_elf.py` is the binary survey.

## Summary

1. **x64: user mode can own FS base.** `WRFSBASE`/`RDFSBASE` are enabled in
   user mode on this Windows 11 build. A written FS base is per thread and is
   never seen by another thread, but Windows does not keep it: it is reset to
   0 whenever the thread is switched out. With base 0 every bionic FS access
   faults, so a vectored exception handler can write the base again and
   retry the instruction ("lazy restore"). Measured: 0 wrong values in 24
   million guarded reads on 16 threads under heavy oversubscription, about
   100 restores per thread per second, 1.1 to 3.7 µs each, so about 0.01% to
   0.04% CPU at worst. Steady-state FS access costs the same as any load.
   No other mechanism works: LDT and descriptor calls return
   `STATUS_NOT_IMPLEMENTED`, and `SetThreadContext` ignores `SegFs`.
2. **ARM64: user mode can own `TPIDR_EL0`** (measured on a 2-vCPU
   Cobalt 100 VM, Windows 11 build 26200). `msr tpidr_el0` works in user
   mode, the value is kept per thread across context switches, exceptions,
   APCs and system calls (0 changes in 1.8 billion checks under load, and
   with 16 threads on 2 vCPUs), and new threads start at 0. Bionic's
   `mrs xN, tpidr_el0` therefore works unchanged; reading the stack guard
   costs 0.07 ns over a plain load. x18 is never changed by the kernel, but
   a fault while x18 is not the TEB kills the process, so x18 must always
   hold the TEB in guest code. The same-length `mrs` to `ldr [x18, #slot]`
   rewrite stays as a fallback only.
3. **x18 survey.** No compiler-generated x18 writes in 4 third-party
   libraries and 3 NDK binaries (2.6 M arm64 instructions in all). The only
   writes come from libunwind (restoring the saved x18 when an exception is
   thrown) and bionic itself (shadow call stack set-up, and `siglongjmp`).
   No shadow-call-stack code was found.
4. **Recommendation: real bionic (option A).** On x64 the thread
   pointer lives in FS base, with lazy restore. On ARM64 it lives in
   `TPIDR_EL0`, set once per thread by `__set_tls`, with no restore and no
   code patching. Bionic needs two small `ANDRUNA` patches: `__set_tls`
   and skipping the shadow call stack set-up on ARM64 (x18 must stay the
   TEB).

## 1. x64: FS base

### What the machine does

| Probe | Result |
| --- | --- |
| CPUID.7.0:EBX[0] (FSGSBASE) | 1 |
| FS / GS selectors in a 64-bit process | 0x53 / 0x2B |
| `RDGSBASE` | works, equals the TEB (`gs:[0x30]`) |
| `RDFSBASE` | works, 0 |
| `mov rax, fs:[0]`, `fs:[0x28]` before any change | access violation (base 0, the first 64 KiB are never mapped) |
| `mov fs, 0x2B` / `0x53` / `0` | allowed; base stays 0 |
| `mov fs, 0x07` (LDT selector) | #GP, reported as access violation |
| `NtQueryInformationThread(ThreadDescriptorTableEntry)` | `STATUS_NOT_IMPLEMENTED` (0xC0000002) for every selector |
| `NtSetLdtEntries`, `NtSet/QueryInformationProcess(ProcessLdtInformation, ProcessLdtSize)` | `STATUS_NOT_IMPLEMENTED` |
| `SetThreadContext` with `SegFs` = 0x2B or 0 | call succeeds, the thread still sees selector 0x53 and base 0 |
| **`WRFSBASE`** | **works in user mode**; `fs:[0]` and `fs:[0x28]` then read through the new base |

### Does a written FS base survive?

Each line writes a base, does the action, then checks `RDFSBASE`. "Reset"
means the value read back was 0; "foreign" would be another thread's value.

| Situation | Checks | Reset to 0 | Foreign |
| --- | ---: | ---: | ---: |
| `Sleep(0)` x3000, idle machine (no switch happens) | 3000 | 0 to 3 | 0 |
| File system calls x3000, idle | 3000 | 9 to 17 | 0 |
| `Sleep(1)` x300, idle (always a switch) | 300 | 300 | 0 |
| Busy loop 2 s, CPU hogs on every core | 90 M to 305 M | 359 to 1201 | 0 |
| `Sleep(0)`/`Sleep(1)`/`SwitchToThread` x3000, loaded | 3000 | 3000 | 0 |
| Access violation handled by a VEH x3000, loaded | 3000 | 10 to 37 | 0 |
| User APC x3000, loaded | 3000 | 7 to 14 | 0 |
| File calls + 64 KiB heap allocations x2000, loaded | 2000 | 142 to 297 | 0 |
| Another thread does Suspend + Get/SetThreadContext x2000 | 0.08 M to 1.6 M | 0 to 199 | 0 |
| 16 threads with their own base, 1 s, loaded | 4.5 M to 6 M | 1350 to 1542 | 0 |

Conclusion: the base is kept across system calls, exceptions, APCs and
interrupts as long as the thread keeps its processor, and is reset to 0
when the thread is switched out. It never leaks between threads. The few
resets in the exception, APC and file lines match the preemption rate.

### Lazy restore

Each guest thread registers its thread pointer. The VEH, on an access
violation, checks that the faulting instruction has an FS prefix (0x64) and
that FS base differs from the registered value, then executes `WRFSBASE` and
returns `EXCEPTION_CONTINUE_EXECUTION`, so the same instruction runs again.
The write done inside the handler survives `NtContinue`.

- Positive offsets (bionic TLS slots, `fs:0x28` stack guard) hit the
  unmapped first 64 KiB. Negative offsets (x86_64 ELF TLS is variant II,
  below the thread pointer) give a non-canonical address and #GP, which
  Windows also reports as an access violation. Both were tested:
  `fs:[-16]` with base 0 restored and read the right value.
- 16 threads, 2 s, 16 CPU hogs on 8 threads, `Sleep(0)` every 8000 reads:
  24.2 M to 29.3 M guarded reads, **0 wrong values**, 95 to 115 restores
  per thread per second.
- At about 100 restores per second and 1.1 to 3.7 µs each, the overhead is
  0.01% to 0.04% of a thread under heavy contention, less when idle.

The VEH must be the first handler (it is registered with `First = 1`) and
must run before ART's fault handler and lx's signal delivery.

### Costs (ns per access, throughput in a tight loop)

| Mechanism | ns | Note |
| --- | ---: | --- |
| `mov rax, fs:[0x28]` with FS base set (lazy restore) | 0.24 to 0.42 | Same as the loop itself: one L1 load |
| `mov rax, gs:[TlsSlots+8*i]` (in-place patch target) | 0.23 to 0.47 | Same |
| `gs:[slot]` then `[tp+0x28]` | 0.39 to 0.55 | Two dependent loads |
| `call` stub doing the two loads (5-byte patch) | 0.47 to 1.59 | |
| Rust `thread_local!`, non-inlined call | 0.49 to 1.48 | Reference |
| `TlsGetValue` | 1.15 to 1.54 | Reference |
| `RDFSBASE` | 2.3 to 4.7 | Not needed on the fast path |
| `WRFSBASE` | 4.6 to 19 | Cost if FS base were switched at every guest/host transition |
| Lazy restore (reset, fault, VEH, `WRFSBASE`, retry) | 1080 to 3710 | Once per switch-in, not per access |
| Fault and emulate every access | 1170 to 3700 | Per access: ruled out |

- **In-place patching** of app code works for every instruction seen: all
  are `fs:disp32` with a SIB no-base encoding, which becomes the same
  `gs:disp32` encoding pointing at TEB `TlsSlots`. If the guest thread
  pointer itself is `&TEB.TlsSlots[k]` (bionic needs about 10 slots, 80
  bytes), then `fs:[8*i]` maps to `gs:[0x1480 + 8*(k+i)]` and the patch is
  one prefix byte plus the displacement. The cost is a copy-on-write page
  for every patched page and a scan at load time. ELF TLS register forms
  (`fs:(%rcx)`) are 3 to 5 bytes, too short for a jump; they would need a
  trap (µs each) or relocation of the basic block. They appear only in
  bionic in this sample, and our bionic can be built differently.
- **Compiler flags for our own code**: our bionic and our libraries can use
  any TLS access we choose, but app libraries are prebuilt, so flags do not
  remove the need for a mechanism.
- **Trap on every access**: 1.2 to 3.7 µs per access, and the stack guard
  alone is read twice per protected call. Not viable.

## 2. ARM64: TPIDR_EL0, TPIDRRO_EL0, x18 (measured on a hosted VM)

What is documented (Microsoft, "Overview of ARM64 ABI conventions"):

- x18: reserved platform register; in user mode it points to the TEB.
- `TPIDR_EL0`: "Reserved."
- `TPIDRRO_EL0`: the current CPU number.
- `TPIDR_EL1`: the KPCR (kernel only).

**Conclusion: on Windows 11 ARM64 user code can own `TPIDR_EL0`.**
Windows saves and restores it per thread across context switches,
exceptions, APCs and system calls, starts new threads at 0, and never
shows one thread's value to another. Spike S8 confirms it end to end:
the arm64 libbase suite (stack guard read from `TPIDR_EL0 + 0x28` in every
protected function) ran on this runner with the loader's `msr tpidr_el0`
and gave the same results as x64 (S8 section 7).

x18 (`x18-clobber`, separate process):

- x18 set to a bogus value inside a 2-billion-iteration call-free loop
  under load: **changed by the kernel 0 times**. Interrupts and
  preemption save and restore the user value of x18; Windows does not
  reload it from the TEB.
- An access violation taken while x18 is bogus **kills the process**
  (exit 0xC0000005, the VEH result is never printed). Exception dispatch in
  user mode (ntdll, or the VEH itself) relies on x18 being the TEB. The run
  did not separate the two.

Rule for the boundary: **x18 must hold the TEB whenever guest code can
fault or call into Windows**, which is always. Guest code built for Android
does not allocate x18 (section 3), so the rule holds as long as bionic's
shadow call stack set-up is patched out. A library that writes x18 cannot be
fixed by a thunk alone, because a fault while x18 is wrong is fatal.

Costs (ns per access, tight loop, 2 vCPU VM; empty loop 0.30 ns):

| Mechanism | ns | Note |
| --- | ---: | --- |
| `mrs tpidr_el0` then `ldr [tp, #0x28]` (bionic native) | 0.37 | 0.07 above the loop |
| `ldr [x18 + TlsSlots]` (in-place rewrite target) | 0.30 | same as the loop |
| `ldr [x18 + slot]` then `[tp + 0x28]` | 0.30 | |
| `msr tpidr_el0` (cost if a thunk switched it) | 1.22 | not needed: Windows preserves it |
| `TlsGetValue` | 0.84 | reference |
| Rust `thread_local!`, non-inlined | 0.75 | reference |

So option 1 of the list below holds: bionic works unchanged with the
thread pointer in `TPIDR_EL0`, set once per thread in `__set_tls`, at the
cost of one `mrs`. The in-place `mrs` rewrite (option 3) is not needed; it
stays a documented fallback if a future Windows build or ARM64EC process
starts using `TPIDR_EL0`.

Options considered before the measurement, in order of preference:

1. `TPIDR_EL0` is preserved per thread: bionic works unchanged, at the
   cost of one `mrs`. **Measured: this is the case.**
2. It is reset like FS base on x64: lazy restore is impossible because an
   `mrs` never faults. Not the case.
3. In-place rewrite: `mrs xN, tpidr_el0` and `ldr xN, [x18, #imm]` are both
   one 4-byte instruction; `#imm` = `0x1480 + 8*k` fits the scaled 12-bit
   offset. Fallback only.

## 3. x18 survey (arm64)

Instructions that write x18 or w18 (destination, load-pair destination,
atomics, base writeback), found with llvm-objdump (LLVM 21, NDK r30):

| Binary | Instructions | x18 writes | Where | `mrs tpidr_el0` | `msr tpidr_el0` |
| --- | ---: | ---: | --- | ---: | ---: |
| NDK r30 `libc++_shared.so` | 183,420 | 1 | `ldp x18, x19` in libunwind `__libunwind_Registers_arm64_jumpto` | 508 | 0 |
| Conscrypt 2.5.3 `libconscrypt_jni.so` | 299,006 | 0 | (2 x18 "reads" are SHA-512 constants decoded as code) | 993 | 0 |
| AndroidX SQLite bundled 2.5.0 `libsqliteJni.so` | 293,064 | 0 | | 354 | 0 |
| JNI helper library (Apache-2.0, 0.7.0) `libfbjni.so` | 19,639 | 1 | libunwind `jumpto`, linked statically | 87 | 0 |
| NDK r30 `simpleperf` (static, platform build) | 823,977 | 1 | libunwind `jumpto` | 2181 | 0 |
| NDK r30 `lldb-server` (static) | 764,547 | 2 | libunwind `jumpto`; bionic shadow call stack set-up (`mov x18, x19`) | 461 | 1 |
| NDK r30 bionic `libc.a` | 230,899 | 3 | `__init_additional_stacks` (shadow call stack set-up); `siglongjmp` (2: keeps the high bits of x18, restores the low 14) | 163 | 2 |

Shadow-call-stack prologues (`str x30, [x18], #8`): 0 in every file.

Reading:

- Clang reserves x18 for Android arm64 targets, so compiled NDK code does
  not allocate it. The libunwind write restores the x18 value captured on
  the same thread by `unw_getcontext`, which on Windows is the TEB, so it is
  harmless.
- Bionic always sets x18 to a shadow call stack for each thread on arm64.
  On Windows ARM64 that would destroy the TEB pointer: the `ANDRUNA` bionic
  patch must skip it (no shadow call stack on WoA). `siglongjmp` only
  changes x18's low 14 bits back to what `sigsetjmp` saw on the same thread,
  so it is harmless once x18 is not changed elsewhere.
- Shadow call stack builds (`-fsanitize=shadow-call-stack`) are used by the
  platform; none of the app libraries in the sample uses it.
- Risk not covered by this sample: old libraries built with GCC (removed
  from the NDK in r18, 2018), which treats x18 as a scratch register, and
  hand-written assembly. A larger sweep of real APKs is needed (phase 5); a
  library found writing x18 would need its x18 writes patched or the thunk
  to restore x18 on every callback into Windows code.

Not downloaded (slow network, about 12 KB/s per connection): the full NDK
and larger app libraries (game engines, media libraries). The NDK files above
were fetched as single zip entries with range requests.

## 4. Recommendation

- **Real bionic (option A).** No TLS reason forces a shim: on x64 FS base
  works with lazy restore; on ARM64 either `TPIDR_EL0` works or a
  same-length rewrite does. Confirm in round 2 by loading an NDK library on
  real bionic.
- **x64 TLS:** thread pointer in FS base, set at thread creation with
  `WRFSBASE`, restored by the first-chance VEH on the first FS fault after a
  switch. No patching of app code. Keep the in-place `fs:disp32` to
  `gs:TlsSlots` patch as the fallback and test it in CI so it is ready.
- **ARM64 TLS:** thread pointer in `TPIDR_EL0`, written once per thread
  in `__set_tls`; Windows preserves it (section 2). A start-up self-test
  should write a value, force a switch (`Sleep(1)`) and read it back, and
  pick the in-place `mrs` rewrite if the value is lost. x18 stays the TEB
  at all times; the shadow call stack set-up is patched out.
- **Bionic patches (`defined(ANDRUNA)`):** `__set_tls` registers the thread
  pointer with lx (x64: lazy restore list; ARM64: per the tests); no shadow
  call stack set-up on ARM64.
- **ADR needed** now that both are measured: thread pointer mechanism per
  architecture and the dependency on undocumented behavior (`WRFSBASE` in
  user mode on x64, a preserved `TPIDR_EL0` on ARM64). ARM64 evidence is
  from one hosted VM; confirm on a physical Snapdragon X machine before the
  ADR is accepted.

## Risks and open points

- `WRFSBASE` in user mode is undocumented on Windows. It depends on the CPU
  (every CPU supported by Windows 11 has FSGSBASE) and on Windows setting
  CR4.FSGSBASE. Seen here on build 26300 with VBS on. To check: Windows 11
  23H2 and 24H2, an AMD CPU, a Hyper-V guest, and CI runners. A start-up
  self-test must pick the fallback if `WRFSBASE` raises #UD.
- Also seen on the GitHub-hosted x64 runner (AMD EPYC 9V74 VM, Windows
  Server 2025 build 26100, VBS running): `WRFSBASE` works, the base is
  reset to 0 on a switch and never leaks, lazy restore gave 0 wrong values
  in 5.1 M reads (627 restores), and a restore costs 1.6 µs. The x64
  Suspend + Get/SetThreadContext line has the same not-started bug as the
  first ARM64 run (0 checks) and was not fixed in `x64.rs`.
- If Windows ever starts to preserve FS base, lazy restore simply stops
  firing; if it starts to set FS base to something else (non-zero, mapped),
  stale-base reads would not fault. The start-up self-test should also check
  that a switched-out thread comes back with base 0.
- An FS access inside a region where the VEH cannot run (for example while
  the loader lock is held by a crashing thread) would be fatal; the VEH must
  not take locks or allocate.
- Not measured: real context-switch rates of a running Android app, the cost
  of the in-place patch scan at load time.
