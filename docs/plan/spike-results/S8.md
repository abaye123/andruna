# S8 results: AOSP built as Android ELF

**Status:** round 1, 2026-11-26. On x64: liblog, libbase, libc++ and
libbase's gtest suite were built for `x86_64-linux-android` as ELF, loaded
into a Windows process by a prototype ELF loader, linked to andruna-lx
through System V entry points, and run: **328 of 367 libbase tests
pass**. On arm64: the same objects were built for `aarch64-linux-android`
and the loader for `aarch64-pc-windows-gnullvm`; the arm64 objects were
mapped and relocated on x64 (link-only mode) but **not run** (no ARM64
machine). The decision is drafted as
[ADR 0013](../../decisions/0013-aosp-binary-format.md) (proposed).

Code: [`spikes/s8/`](../../../spikes/s8/) (standalone Cargo project, not in
the workspace), plus an ELF toolchain file and compilation environment in
[`aosp/cmake/`](../../../aosp/cmake/).

```
cargo xtask fetch                               # AOSP at the pinned tag
git clone --depth 1 --filter=blob:none --sparse --branch llvmorg-23.1.6 \
    https://github.com/llvm/llvm-project out/s8/llvm-project
git -C out/s8/llvm-project sparse-checkout set libcxx libcxxabi libunwind \
    runtimes cmake llvm/cmake llvm/utils/llvm-lit compiler-rt/lib/builtins libc
python spikes/s8/guest/build.py --arch x64      # sysroot libc libcxx aosp
python spikes/s8/guest/build.py --arch arm64    # adds the builtins step
cd spikes/s8
cargo build --release --target x86_64-pc-windows-gnullvm   # llvm-mingw on PATH
python run_tests.py                             # the libbase suite
andruna-spike-s8 bench | run <exe> [args] | load <so> | unwind | crash
```

`llvmorg-23.1.6` is the tag of the llvm-mingw clang (`clang --version`
prints the commit); libc++ must match the compiler's headers.

## Machine and method

| Item | Value |
| --- | --- |
| CPU | Intel Core Ultra 7 258V (4 P + 4 LP E cores, 8 threads) |
| OS | Windows 11 Pro, build 26300 |
| Load | Shared development machine; about 35% background CPU load from other agents |
| Toolchain | llvm-mingw 20261117 (clang 23.1.6), Rust 1.92.0, `x86_64-pc-windows-gnullvm`, release build |

## Summary

1. **AOSP builds as Android ELF with no source change and no data-model
   work.** The module files of `aosp/` build unchanged for
   `x86_64-linux-android10000` and `aarch64-linux-android10000` with
   bionic's headers as they are (`ANDRUNA` is not defined, the bionic
   patches stay inactive). Layers 1 and 2 (liblog, libbase, libcutils,
   libutils, libz, liblz4, libziparchive, libartpalette, libtinyxml2,
   libartbase, libdexfile) compile completely; of libart's 238 sources, 223
   compile and the other 15 fail only on generated headers and projects not
   built yet, the same kind of list as S1 round 2 (plus libunwindstack,
   not fetched for this spike). The LLP64 differences of S1
   (`struct stat`, `sigset_t`, `pthread_t`, `tv_nsec`, `jmp_buf`, ART's
   x86 fault handler, arm64 `long double` and variadics) do not exist in
   this build.
2. **A small loader is enough to run real AOSP code.** About 1,900 lines of
   Rust map PT_LOAD with lx's `mmap`, apply RELA, Android `APS2` packed
   relocations, RELR, GLOB_DAT/JUMP_SLOT, TLS relocations and TLSDESC, bind
   against the loaded objects and a host table, protect RELRO, run init
   arrays, lay out static ELF TLS under the thread pointer (FS base with
   S4's lazy restore), and create guest threads.
3. **libbase's tests run.** 328 of 367 pass. The rest fail on
   what lx and the spike's libc do not have yet (fork for death tests,
   sockets, `ftruncate`, symlinks, file modes, file-backed `mmap`,
   `/proc`), not on the binary format (section 3).
4. **The boundary is cheap.** A guest call into lx costs about 0.45 ns more
   than the same call made from Windows-ABI code (0.9 ns vs 0.44 ns for
   `gettid`); a host-to-guest call costs about 0.4 ns more than a
   Windows-to-Windows call, because the System V callee may clobber
   `rsi`, `rdi` and `xmm6`-`xmm15`.
5. **Debugging works with LLDB, not with Windows debuggers by themselves.**
   llvm-mingw's `lldb.exe` shows guest functions, source lines, arguments,
   and unwinds from guest frames through Rust frames to
   `RtlUserThreadStart`, after two commands per object that the loader
   writes out. Windows' own unwinder stops at the first guest frame unless
   unwind tables are registered; the spike translates `.eh_frame` into
   `RUNTIME_FUNCTION`/`UNWIND_INFO` and `RtlVirtualUnwind` then walks
   through guest frames correctly. WinDbg (cdb from the current WinDbg
   package) then shows correct stacks, with guest frames as
   `object+offset`, but no guest symbols or lines.
6. **Recommendation: build AOSP as Android ELF (option 3 of S1)**, with
   andruna-linker in phase 1 and real bionic (S4) as the guest libc. Option
   1 stays the fallback.

## 1. Building AOSP as Android ELF

[`aosp/cmake/toolchain-android-elf.cmake`](../../../aosp/cmake/toolchain-android-elf.cmake)
uses llvm-mingw's own clang with `--target=<arch>-linux-android10000`
(Soong's "current" API level), a sysroot made from bionic's headers
(`libc/include`, the kernel UAPI, `asm-<arch>`, laid out as the NDK's),
`ld.lld` with Android's link flags (`--pack-dyn-relocs=android+relr`,
`--hash-style=gnu`, `-z now`, `-z relro`, 4 KiB pages on x64 and 16 KiB on
arm64) and compiler-rt builtins linked into each object, as Android does.
[`aosp/cmake/android-elf.cmake`](../../../aosp/cmake/android-elf.cmake)
replaces `android.cmake` for this toolchain (an `ANDRUNA_AOSP_ELF` switch
in `aosp/CMakeLists.txt`): no `-nostdinc`, no undefined Windows macros, no
`data_model.h`, no `-mno-ms-bitfields`; clang's Android target already is
LP64 with 32-bit `wchar_t`, `__ANDROID__`, `__linux__` and ELF TLS. The
stack protector (`-fstack-protector-strong`) is passed explicitly, as
Soong does; it reads the guard at `%fs:0x28` on x64.

What the guest needs besides AOSP:

| Piece | How the spike provides it | Product |
| --- | --- | --- |
| libc | A shim, `guest/libc` (2,600 lines of C: string, stdio with a printf engine, stdlib, ctype, UTF-8 wide characters, one C.UTF-8 locale, time, error strings) plus host functions in Rust (2,600 lines: files, memory, time and futex through lx; threads, allocation, directories, properties) | Real bionic built as ELF with its system calls routed to lx (S4) |
| libc++ / libc++abi | Built from LLVM at the compiler's tag with the runtimes build, against the sysroot, `-fno-exceptions` | The same, or AOSP's `external/libcxx` |
| Compiler runtime | llvm-mingw ships `libclang_rt.builtins-x86_64.a` for Linux; for arm64 `build.py` compiles compiler-rt's builtins (271 objects, including the outline atomics Android code calls) | The same |
| `crtbegin_so.o` | One hidden `__dso_handle` per object | bionic's |

The guest objects link against `libandruna_host.so`, a stub with one empty
function per name of
[`host_symbols.txt`](../../../spikes/s8/guest/libc/host_symbols.txt) (176
names), the way NDK code links against stub libraries. The loader binds
those names to its host table; `andruna-spike-s8 check` verifies the table
covers the list.

Built objects (x64, `-O2 -g`): `libc.so` 124 KiB mapped, `libc++.so.1` 1.2
MiB, `liblog.so` 80 KiB, `libbase.so` 240 KiB, `libbase_test` (a PIE) 2.1
MiB.

## 2. The loader

[`spikes/s8/src/loader.rs`](../../../spikes/s8/src/loader.rs),
[`tls.rs`](../../../spikes/s8/src/tls.rs),
[`elf.rs`](../../../spikes/s8/src/elf.rs):

- Breadth-first `DT_NEEDED` loading; each object reserves its span
  `PROT_NONE` with `andruna_lx::mem::mmap`, then maps each segment
  `MAP_FIXED` inside it and copies the file bytes (lx has no file-backed
  mappings yet). Only the loadable part of the file is read; debug
  sections stay on disk.
- Relocations: RELA, `DT_ANDROID_RELA` (`APS2`, decoded as bionic's
  `packed_reloc_iterator`), `DT_RELR` (and Android's older tag), JMPREL,
  `RELATIVE`, `64`/`ABS64`, `GLOB_DAT`, `JUMP_SLOT`, `IRELATIVE`,
  `DTPMOD64`, `DTPOFF64`, `TPOFF64`, `TLSDESC` (static resolver, needed on
  arm64 where Android's TLS model is TLSDESC). For the libbase suite:
  13,073 relocations, 8,606 of them RELR and 3,255 from packed tables.
- Symbol binding: the loaded objects in load order (`.dynsym`, sizes from
  `DT_GNU_HASH`), then the host table, then a stub that reports the call
  and fails with `ENOSYS` (none were needed). No symbol versioning, no
  namespaces, no `dlopen`.
- `PT_GNU_RELRO` made read-only after relocation; `DT_PREINIT_ARRAY`,
  `DT_INIT`, `DT_INIT_ARRAY` run with `(argc, argv, envp)`.
- Static TLS, x64 variant II with bionic's slot layout at the thread
  pointer (slot 0 = self, slot 5 = stack guard at `%fs:0x28`), arm64
  variant I with the 64-byte slot area. The thread pointer is the FS base
  (`WRFSBASE`), restored by the first vectored handler when Windows has
  reset it (S4). `__tls_get_addr` reads the current thread pointer from
  the host's own TLS, so it is right even while the FS base is stale.
- Guest threads (`pthread_create`) are Windows threads with a fully
  committed stack: Linux code does not probe the stack page by page, and a
  frame larger than a page could jump over the Windows guard page.

## 3. libbase tests

`run_tests.py` runs the suite; a test that ends the process is recorded and
excluded, and the suite runs again.

| Result | Tests | Cause |
| --- | ---: | --- |
| Passed | **328** | strings, parse*, file I/O, logging to stderr and logd fallbacks, threads, chrono, properties, errors, result, expected, scopeguard, test_utils, ... |
| Ended the process: death tests | 11 | `EXPECT_DEATH`/`ASSERT_DEATH` (logging.CHECK, LOG_FATAL, PLOG_FATAL, LOG_FATAL_NOOP_ABORTER, no_destructor.bomb and defused, five result.*): gtest forks, the spike has no `fork` or `pipe` |
| Ended the process: sockets | 16 | CmsgTest: `socketpair` (lx has no sockets yet) |
| Ended the process: `ftruncate` | 2 | TestUtilsTest.CaptureStdout_smoke, CaptureStderr_smoke: lx does not export `ftruncate` and the spike cannot reach lx's handles |
| Ended the process: file `mmap` | 1 | mapped_file.smoke: lx returns `ENOSYS` for file-backed mappings |
| Failed | 9 | symlink and Readlink (no symbolic links), WriteStringToFile2 (lx reports fixed file modes), RemoveFileIfExists_EACCES (permissions), ForkSafe (fork), process.find_ourselves (`/proc`), VerifyRunningWithScudo (the shim's allocator is not Scudo), properties.too_long (the shim's property store accepts the long name), CachedProperty_WaitForChange (reads the value before any property exists; not investigated) |
| Total listed | 367 | |

No failure comes from the binary format or the loader: every one is a
missing lx feature or a shortcut of the spike's libc. With the 30
process-ending tests filtered out the suite runs in 2.24 s. The guest main
thread took 137 and 159 FS-base lazy restores in two runs (about 65 per
second; every stack-protected function reads `%fs:0x28`, 2,265 such reads
in the test binary, 334 in libbase, 1,133 in libc++), with no wrong
value seen by any test.

## 4. Boundary cost

`andruna-spike-s8 bench` (guest loops in `guest/bench/bench.c`, 10 M calls,
best of 5; three runs gave the same values within 10%):

| Call | ns per call |
| --- | ---: |
| guest -> guest, indirect call of an empty function | 0.65 to 0.70 |
| guest -> host, empty System V function | 0.42 to 0.45 |
| guest -> host -> lx `gettid` (Windows convention inside) | 0.84 to 0.91 |
| host -> lx `gettid` directly (what option 1 does) | 0.42 to 0.46 |
| guest -> host -> lx `clock_gettime(CLOCK_MONOTONIC)` | 33.2 to 33.7 |
| guest -> guest libc `strlen` (11 bytes, shim's byte loop) | 1.9 to 2.1 |
| guest TLS variable `++` in a loop (general dynamic, call hoisted) | 0.21 to 0.22 |
| host -> guest, empty function (System V call from Rust) | 1.06 to 1.15 |
| host -> host, empty function (Windows convention) | 0.64 to 0.67 |

Reading: entering lx from guest code adds one call level and the
argument shuffle, about 0.45 ns, which is 1.3% of a `clock_gettime` and
nothing next to a real system call. The other direction (callbacks,
`pthread_create` start routines, JNI from ART into natives) adds about
0.4 ns, the cost of saving the registers the Windows convention keeps and
System V does not. The guard (`catch_unwind`) around each host function
costs nothing on the normal path.

Stack guard and TLS: guest code reads the stack guard at `%fs:0x28` and
TLS through the loader's layout; `bench` checks the guard is non-zero.

## 5. Load time

`andruna-spike-s8 load libbase_test` (5 objects, 3.7 MB of loadable
segments; 5.0 MB read with `.symtab` for crash reports), five runs:

| Step | ms |
| --- | ---: |
| Read, map, parse dynamic sections, build export tables | 6.1 to 11.7 |
| Relocate and protect (13,073 relocations, 2,429 lookups) | 0.9 to 2.1 |
| Initializers (all objects) | 0.25 to 0.44 |
| Total | 7.5 to 14.2 |

For scale, `LoadLibraryW` of llvm-mingw's `libc++.dll` (2.0 MB) takes
0.5 ms warm (7.7 ms the first time). The prototype copies every segment
into private memory and hashes every export into a `HashMap` at load; a
product loader maps files with section views (shared between processes,
which also matters for memory), looks symbols up through `DT_GNU_HASH`,
and should land near the Windows loader. Not measured: cold start from
disk, and many-process memory sharing.

## 6. Debugging

### LLDB

llvm-mingw's `lldb.exe` debugs the spike process natively. The loader
writes, for each object, `target modules add <path>` and
`target modules load --file <name> --slide <bias>` (`S8_LLDB_FILE`). After
`command source` of that file, a fault in guest code
(`andruna-spike-s8 crash`) shows:

```
* thread #5, stop reason = Exception 0xc0000005 ... Access violation reading location 0x00000010
  * frame #0: libs8bench.so`s8_crash_leaf(p=0x0000000000000010) at bench.c:85:71
    frame #1: libs8bench.so`s8_crash_middle(p=0x0000000000000010) at bench.c:86:73
    frame #2: andruna-spike-s8.exe`andruna_spike_s8::cmd_crash::{closure}... at main.rs:175:16
    ...
    frame #14: kernel32.dll`BaseThreadInitThunk + 23
    frame #15: ntdll.dll`RtlUserThreadStart + 44
```

Guest symbols, DWARF line tables, arguments and `.eh_frame` unwinding all
work, from guest frames into the host frames that called them, with
`frame select` and source listing. The product would register objects
automatically (the in-memory JIT registration interface LLDB supports,
`__jit_debug_register_code`, or a small LLDB plug-in); not tried.

### Windows unwinding

`andruna-spike-s8 unwind` calls a host function through two guest frames
and walks the stack from there with `RtlLookupFunctionEntry` and
`RtlVirtualUnwind`, as exception dispatch and Windows debuggers do:

- Without unwind tables, Windows treats the guest frame as a leaf, takes a
  random stack slot as the return address and produces garbage frames
  (`0x1`, stack addresses) before finding host frames again by chance.
- With `S8_UNWIND=1` the loader translates each FDE's CFA program into
  `UNWIND_INFO` ([`unwind.rs`](../../../spikes/s8/src/unwind.rs)) and
  registers it with `RtlAddFunctionTable`. The walk is then exact:
  callback, `s8_call_host`, `s8_call_host_outer`, the Rust frames,
  `BaseThreadInitThunk`, `RtlUserThreadStart`. Coverage: 9 entries for the
  bench library (every non-leaf function), 1,110 entries for libc++ with
  500 FDEs not translated, 119 for the libc shim with 42 not translated
  (leaf functions need no entry). The untranslated FDEs are reported as
  "prologue longer than 255 bytes": CFI rows after the prologue (for
  example around calls in functions without a frame pointer) that the
  translation still counts as prologue, a known limitation; those frames
  fall back to the leaf assumption.
- `RtlCaptureStackBackTrace` stops at the first guest frame even with the
  tables registered (apparently it does not use dynamic function tables;
  not investigated); code that needs stacks must use `RtlVirtualUnwind`.
- The translation assumes no `alloca` in frame-pointer functions (Windows
  applies the codes after `UWOP_SET_FPREG` relative to `rsp`) and covers
  x64 only; arm64 unwind codes are a separate format and were not
  attempted.

Why it matters beyond debuggers: Windows exception dispatch walks frames
the same way. A Windows exception (or a Rust panic, which unwinds with
SEH on gnullvm) that has to pass guest frames needs these tables; without
them the dispatch misreads the stack. The VEH-first design (S1, S4)
handles faults before any frame walk, so lx's own signal delivery does
not depend on it.

### WinDbg and Visual Studio

Tested with `cdb.exe` from the current WinDbg package (unpacked, not
installed), on the same `crash` fault:

- Without unwind tables, `k` shows the guest frames as bare addresses and
  one garbage frame (a stack address taken as a return address), then
  finds the host frames.
- With the translated tables (`S8_UNWIND=1`), `k` is exact: the faulting
  leaf, its caller, the host frames, `BaseThreadInitThunk`,
  `RtlUserThreadStart`. dbgeng uses the dynamic function tables.
- `.reload /f /i libs8bench.so=<base>,<size>` (the loader writes these
  lines, `S8_WINDBG_FILE`) names the ranges, so frames read
  `libs8bench+0x1b10`, but WinDbg loads no symbols or line tables from the
  ELF file this way ("no symbols"). WinDbg's support for ELF and DWARF is
  aimed at Linux core dumps; whether it can be used for ELF images inside
  a Windows process was not found.
- Side observation, not about ELF: the Rust host frames are unsymbolized
  too, because Rust's gnullvm targets emit DWARF, not PDB. ADR 0008's
  "CodeView so PDBs work" holds for the C/C++ code built with
  `-gcodeview`, not for Rust code on gnullvm.

Visual Studio was not tried (no scripted way to drive its debugger here).
It uses the same unwinding services, so the same split is expected:
stacks with registered tables, no ELF symbols. Not verified.

### The crash report

Because Windows tools see guest code as anonymous memory, the loader's
exception handler prints its own report for faults in guest code:
object, offset, nearest `.symtab` symbol, and a frame-pointer walk
(guest code keeps frame pointers on Android x64). Example from the suite:

```
[s8] guest fault 0xc0000005 at 0x23b724f646a libbase_test+0xa646a (_ZN35file_RemoveFileIfExists_EACCES_Test8TestBodyEv+0x2a)
[s8]   read from address 0x14
[s8]   #1 0x23b72613220 libbase_test+0x1c3220 (_ZN7testing4Test3RunEv+0x230)
...
[s8]   #6 0x23b725e251b libbase_test+0x19251b (main+0xbb)
```

### Lazy FS-base restore and debuggers

S4's lazy restore takes an access violation after each context switch of a
guest thread. A debugger sees these as first-chance exceptions. LLDB stops
on them by default, so a debugging session on a busy guest thread needs the
access-violation stop turned off or the fault recognized (an LLDB plug-in
or a debugger extension that knows the FS-prefix rule). This is a cost of
S4's mechanism, not of ELF, and applies equally to option 1 if AOSP code
there used `%fs`.

## 7. arm64

- Built: compiler-rt builtins, the libc shim, libc++, liblog, libbase, the
  libbase suite and the bench library for `aarch64-linux-android10000`
  (`build.py --arch arm64`), and the loader for
  `aarch64-pc-windows-gnullvm` (`cargo build --target
  aarch64-pc-windows-gnullvm`; PE32+ ARM64).
- Verified on x64 with `S8_LINK_ONLY=1 S8_ARCH=arm64 andruna-spike-s8 link
  libbase_test`: all five arm64 objects map and relocate (14,474
  relocations, 9,961 RELR, 3,270 packed, TLSDESC in libc++), nothing
  unresolved. No arm64 code was executed.
- Found: Android arm64 uses TLSDESC for TLS in shared objects, and
  outline atomics (`__aarch64_ldadd4_acq_rel` and friends, which read
  `__aarch64_have_lse_atomics` from `getauxval(AT_HWCAP)`); both are in the
  loader and the host table now.
- Not done: running on an ARM64 machine, the `TPIDR_EL0` question (S4),
  arm64 unwind tables, the x18 rule at the boundary (S4: guest code does
  not write x18; the host entry points are plain AAPCS64 functions).

## 8. Comparison with option 1 (Windows target, widened headers)

| | Option 1: Windows target, widened headers | Option 3: Android ELF (this spike) |
| --- | --- | --- |
| **Correctness** | Every `long` in bionic's ABI must be widened by patch and every AOSP store into `long` found (S1: 190 header lines, 298 + 644 narrowing sites to triage, 3 + 1 real bugs found so far); arm64 `long double` stays 64-bit and variadic floating-point arguments differ, with no fix in clang. Each new AOSP project (framework natives, HWUI, Skia) repeats the audit. | Android's ABI exactly: the same objects as on a phone. The only convention boundary is guest -> lx (and back), at a few hundred well-typed entry points generated from one list. |
| **Effort now** | A large mechanical bionic patch (carried for every tag), `compare.py` in CI, small AOSP patches; libc++ and libc++abi built for bionic with Windows object code (S1). | andruna-linker in phase 1 (prototype: 1,900 lines), a guest bionic (S4 option A) with system calls routed to lx, the System V entry layer for lx exports, libc++ built for Android. The loader is needed anyway for app native code (phase 5), so this is earlier, not extra. |
| **Effort later** | Grows with every AOSP project and tag. | Grows with linker features (namespaces, `dlopen`, `android_dlopen_ext`), which phase 5 needs anyway. |
| **Performance** | Direct Windows calls into lx (0.44 ns for `gettid`). | 0.45 ns more per lx call, 0.4 ns more per callback; FS-base lazy restore after context switches (S4: 0.01% to 0.04% of a thread). Load time: prototype 7.5 to 14 ms for libbase and its suite, to be brought near the Windows loader with file mappings. |
| **Debuggability** | PDB/CodeView: WinDbg and Visual Studio show symbols, lines and stacks natively. | DWARF: LLDB (shipped with llvm-mingw) shows everything after registering the objects; Windows debuggers need translated unwind tables for stacks (prototyped) and see no symbols; crash reports come from the loader. |
| **Risk** | Silent layout bugs that compile cleanly (S1: `fstat` writing 16 bytes past a 128-byte buffer). | The loader and guest libc are new code on the critical path from phase 1; Windows tooling (profilers, crash dumps) sees guest code as anonymous memory unless Andruna adds support. |

## 9. Recommendation

Build AOSP code for `<arch>-linux-android` as ELF and load it with
andruna-linker (ADR 0013, proposed). The deciding facts: the same AOSP
sources built and ran with no data-model work at all, the boundary cost is
below half a nanosecond, and the loader is needed for app native code
anyway. The debugging cost is real but bounded: LLDB works today, and
Windows stack walking works with translated unwind tables.

Order of work if accepted: andruna-linker as a crate from this prototype
(file-backed mappings, GNU hash lookups, namespaces later); real bionic for
the guest (S4 round 2) instead of the shim; generated System V entry points
for lx's exports; automatic LLDB registration; arm64 run on a machine.

## Not verified

- Nothing ran on arm64.
- Real bionic: the guest libc is a shim, so stdio, locale, malloc and
  pthread behavior are not bionic's (S4 round 2 covers that).
- C++ exceptions in guest code (`-fno-exceptions` here, as AOSP's platform
  code): needs libunwind for the guest and `dl_iterate_phdr`.
- Visual Studio's debugger (expected to behave as WinDbg; not run).
- WinDbg symbol loading for ELF images in a Windows process (only the
  `.reload /i` form was tried).
- Load time with file-backed mappings; memory sharing between processes.
- ART: libart does not link yet in either build (S1).
