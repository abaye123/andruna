# S7: AppContainer, GPU and warm processes

**Status:** 2026-11-27, x64 run on the development PC (Windows 11 Pro
10.0.26300, Intel Arc 140V GPU), under load from other builds; arm64 not
run. Decisions proposed as [ADR 0035](../../decisions/0035-warm-process-strategy.md)
(warm strategy) and [ADR 0036](../../decisions/0036-appcontainer-file-access-and-sysd-channel.md)
(file access and the sysd channel). Production code:
`crates/andruna-sysd/src/appcontainer/`.

## Question

Do ART, D3D11 and DirectComposition (and ANGLE on them) work inside a
per-package AppContainer, and which warm-process strategy keeps start time
on target ([security](../../spec/04-security.md#warm-processes-and-appcontainer))?

## Answers

- **ART runs inside an AppContainer** (low integrity, AppContainer token,
  package SID, no capabilities except our own `andrunaRuntime`): Hello
  World in the interpreter, with the JIT (also with every method compiled
  at its first call), with AOT code and the boot image; the fault test
  (implicit null checks and stack overflow through VEH and the signal
  path, which needs `WRFSBASE`) passes. Dynamic code (the JIT's executable
  memory) is allowed: the container does not imply arbitrary code guard.
  Nothing in andruna-app, andruna-linker or andruna-lx needed a change.
- **What breaks is file access only**, and only where expected: with no
  grant on the ART root andruna-app stops at once with "the ART root ... is
  incomplete" (exit 2), an honest error. Any of three grants fixes it (see
  below); ADR 0036 proposes a capability of our own.
- **The data directory must have a low mandatory label**, or the
  low-integrity process cannot write its guest tree. Setting the label on
  an existing directory failed with `ERROR_ACCESS_DENIED` in a tree where
  the user had no explicit ACE (the owner has no implicit WRITE_OWNER);
  creating the directory with the full security descriptor works always.
- **sysd pipe:** the named pipe of andruna-ipc with
  `PipeSecurity::allow_app_container` (`(A;;GRGW;;;<package SID>)` and a
  low label) can be opened from the container and answers a ping; without
  that ACE the open fails with access denied. `andruna_ipc::Client::connect`
  fails from the container ("served by process N, which runs as another
  user"): its server check opens sysd's process to read its token, which a
  container may not do. An **inherited anonymous pipe** works with no name
  and no DACL; ADR 0036 makes that the app channel.
- **Boot image sections:** sysd-style mapping works into a container
  process: nine boot image files (36.4 MiB) mapped read-only from
  file-backed sections into a suspended container process in **0.033 ms**,
  the process then reads every page (magic `art\n`, ELF, `vdex` at the
  expected views) while its own `open` of `boot.art` fails with access
  denied. The container needs no access to the image files.
- **D3D11 + DirectComposition work in the container:** hardware device
  (feature level 11_0, Intel Arc 140V), `CreateSwapChainForComposition`,
  `DCompositionCreateDevice`, a target on the window, clear, present,
  commit. Readback of the back buffer and the window content as DWM
  composes it (`PrintWindow` with `PW_RENDERFULLCONTENT`) both have the
  cleared color. Spawn to presented frame 463 ms in the container, 523 ms
  outside (single runs, noisy). The screen itself could not be sampled:
  the session was locked during the run, so the on-screen pixel was the
  lock screen for every variant, container or not.
- **Less privileged AppContainer (LPAC):** ART runs (grant to the
  capability, or to `ALL RESTRICTED APPLICATION PACKAGES`); D3D11 hangs at
  start unless the token also has the `registryRead` capability, then
  works. Not adopted yet (ADR 0036).
- **ANGLE:** not tested. ANGLE is not on `origin/main` yet and no local
  build was found; `s7 angle --angle-dir <dir>` runs the same check with
  ANGLE's EGL (D3D11 platform, `EGL_DIRECT_COMPOSITION_ANGLE` window
  surface) once a build exists.
- **Warm strategy:** the container adds no measurable start time, and
  mapping the boot image costs microseconds, so option 2 (create
  suspended in the right container, map, resume) costs the same as a
  plain cold start. A warm host (option 1) answers an assignment in
  0.5 ms but costs 106 MiB of working set and 1.09 GiB of private commit
  while idle. ADR 0035 proposes option 2, with option 1 reconsidered when
  the framework's start time is known.

## Numbers

### Start times (15 interleaved runs, median [min-max])

andruna-app, Hello World, boot image, JIT, staged as in production (data
directory with the package's descriptor, runtime files through
`andrunaRuntime`). Interleaving runs the three cold variants back to back
in each round, so load from other builds on the machine hits them alike.

| | Spawn to `Hello` | Spawn to exit |
| --- | ---: | ---: |
| Cold, no container | 140.2 ms [124.4-166.1] | 177.0 ms [158.3-204.3] |
| Cold, in the container | 142.0 ms [124.3-183.9] | 175.8 ms [158.1-219.8] |
| Suspended in the container, boot image mapped by the parent, resumed (option 2) | 141.3 ms [124.9-187.9] | 177.7 ms [159.1-224.9] |
| Warm host in the container: spawn to ready | 159.8 ms [129.0-225.9] | |
| Warm host: assignment (one line on stdin) to `Hello` (option 1) | 0.5 ms [0.4-0.9] | |

In option 2 the parent maps the boot image at `0x7_0000_0000`, away from
ART's own image base, because andruna-app still maps the image itself; the
row measures process creation suspended, the mapping and the resume, with
ART then loading its image as in the other rows. An earlier
non-interleaved run gave 168, 193 and 132 ms for the three cold rows:
order effects under load are larger than the container's cost.

Idle warm host (Warm.java waiting on stdin, 300 ms after ready): working
set 105.8 MiB, private commit 1091.5 MiB (`PrivateUsage`). The commit is
the runtime's reservations as lx commits them today, the same for every
app process, but a warm host pays it while doing nothing.

### Install-time costs

| | Time |
| --- | ---: |
| `CreateAppContainerProfile` (or open existing) | 22-61 ms |
| Inheritable ACE on the ART root (37 files, 6 directories) and the staged binaries | 5-29 ms |
| Data directory created with its descriptor | 1.4-9.4 ms |

### Grant options for the runtime files

| Grant on the ART root and binaries | Normal container | LPAC |
| --- | --- | --- |
| None | fails: ART root reported incomplete, exit 2 | (same) |
| `ALL APPLICATION PACKAGES` | Hello runs | n/a (LPAC ignores it) |
| `ALL RESTRICTED APPLICATION PACKAGES` | not tried | Hello runs |
| Package SID | Hello runs | not tried |
| `andrunaRuntime` capability SID | Hello runs | Hello runs |

## What was built

`spikes/s7` (standalone, not in the workspace), one executable with
subcommands; every container test stages its files under `out/s7` and uses
the profile `andruna.s7.test`:

- `s7 art`: andruna-app in the container with a chosen grant
  (`--grant aap|cap|pkg|none`, `--lpac`, `--no-container`, ART options
  after `--`).
- `s7 warm`: the start-time table above. `java/Warm.java` is the warm host
  stand-in: it prints `warm: ready`, waits for a class name on stdin, then
  loads and runs it.
- `s7 pipe`: the andruna-ipc named pipe and an inherited pipe from inside.
- `s7 section`: boot image files mapped into a suspended container
  process.
- `s7 gpu` / `s7 angle`: a window with a composition swap chain cleared to
  a known color; the parent checks the screen and the DWM-composed window
  content. `--caps` adds capabilities.
- `s7 cleanup`: revokes the grants and deletes the profile.

## Production code

`crates/andruna-sysd/src/appcontainer/` implements what the spike showed:
per-package profiles (`install`, `uninstall`, `sandbox`, salted names),
directory descriptors, the runtime capability grant, capabilities from
granted permissions, `launch` with `SECURITY_CAPABILITIES`, a handle list,
an optional job and suspended start, a minimal environment, and
`process_sid`/`pid_sid` for Binder peer identity.
`crates/andruna-sysd/tests/appcontainer.rs` runs Hello World in a
package's container through that path and checks that the package cannot
read a file outside its grants or another package's data.

## Not verified

- ANGLE inside the container (no build available).
- The screen pixel of a container window (session locked during the run);
  the composed window content was verified instead.
- A framework app or a first frame drawn by app code: neither the
  framework nor the compositor path exists yet.
- ART using a boot image mapped by sysd (andruna-app maps its own); the
  mapping itself and its cost are measured.
- Networking with `internetClient`, AF_UNIX sockets and lx's named kernel
  objects inside the container (Hello World does not use them).
- arm64, and numbers on a quiet machine.

## Reproduce

```
cargo build -p andruna-app --release
python spikes/s7/java/build_warm.py          # needs build_boot.py's output
cd spikes/s7
cargo build --release
target\release\s7.exe art --grant cap
target\release\s7.exe art --grant cap --dex faults.dex --class Faults -- --mode jit "-Xjitthreshold:0"
target\release\s7.exe art --grant none
target\release\s7.exe art --grant aap --lpac
target\release\s7.exe warm --runs 15
target\release\s7.exe pipe
target\release\s7.exe section
target\release\s7.exe gpu
target\release\s7.exe gpu --lpac --caps registryRead
target\release\s7.exe cleanup
```
